# V1 技术架构与复用

## 继承基线，不重做研究

原完整研究保存在 `archive/recovery-source/Always_On_Voice_Design.pdf` 及其技术附件。它提出 SwiftUI/AppKit、AVAudioEngine/Core Audio、FluidAudio/Silero、Apple Speech、WhisperKit、SQLite/GRDB、Accessibility 等路线。本轮没有重做模型竞赛，也没有重新验证其历史版本号、全部许可证或市场资料。

首个工程候选继续使用 Apple SpeechAnalyzer/SpeechTranscriber；WhisperKit 为替代路径。理由来自原报告的系统集成与维护成本判断，而不是已证明中文识别最优。启动正式工程时核对 SDK、中文语言资产和依赖版本，并用同一批普通话、中英混说、数字、否定词和专业词样本比较。

若候选不达标，应允许有明确授权的在线或混合 ASR，而不是为“本地优先”牺牲体验。V1 不为这个可能性先实现多套推理系统；只保留 SpeechEngine 的能力和处理位置边界。

## 数据通路

麦克风 → 有界音频缓冲 → VAD/保留范围 → 原音日志与流式识别并行 → 文本版本库 → 输入板/历史 → 独立输入操作。

保存责任与实时识别可以并行，不必整段录完才出字。“原音已保存”只依据真实持久化水位。ASR、UI 或目标应用失败不能停止后续音频落盘。

实时回调不写磁盘/数据库、不等待 ASR。文件分块、识别会话和视觉段落是不同边界。原报告的 1 秒预录、800 ms 尾静默、15 秒物理块、1 秒同步均只是 P0 起点，不是实测保证。

## 当前可执行资产

- `contracts/schema.sql`：原结构加独立音频删除意图、audio_epoch、派发绑定/游标/快照与保护约束。
- `contracts/Contracts.swift`：Foundation 可编译接口；含设备/在线引擎边界、独立音频删除协议和 DirectDispatchLedger。
- `model/reference_store.py`：SQLite 与合成文件上的设计参考模型，用于验证事务和恢复语义；不是生产音频实现。

不把 Python 模型嵌入正式 Mac App。原生版复用同一契约，以 Swift/GRDB 实现。不要因本轮已有参考代码就绕过真实音频工程。

## 输入集成

先做明确目标的主动插入，再做连续直接输入。使用目标控件支持的局部插入或原生粘贴，不读取全文再覆盖。不发 Return、不发送消息、不清除已有附件。

运行时目标由应用、窗口、编辑控件、绑定会话和必要的页面语义共同界定。数据库里只保存审计标识；重启后不能用标签重建可执行目标。SPA 切换可能复用编辑节点，原生验收必须验证，不以元素句柄不变判定聊天没变。

复制成功、已尝试投递、确认插入分开。只有有可靠局部结果证据时才显示“已插入”。不能可靠确认时保留文字，允许后续独立段继续；不自动重发。

## 重要取舍

SQLite 事务可以原子更新本地派发意图和游标，不能与外部应用粘贴形成跨应用原子事务。因此本设计追求范围级“至多一次自动尝试”，不是“恰好一次交付”。崩溃发生在记录派发后、实际粘贴前，可能需要用户主动复用该段；不能用自动重试掩盖风险。

本轮查阅的 SQLite 事务文档明确支持 IMMEDIATE 写事务与单写者模型；参考实现据此在同一事务内校验/预留，而不是先检查再单独写入。参考：https://www.sqlite.org/lang_transaction.html 。Apple isFinal/NSRange 官方入口见来源索引；其完整动态正文未在本轮重新取得，不把历史解释标成此次全面复核。
