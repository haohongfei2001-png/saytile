# 1.0.1 性能诊断与验收口径

原 1.0.0 的 5.451 秒首显 FAIL 原件继续保留。单调时钟分解：worker ready 1.181 秒，首个 800 ms 音频解码耗时 4.231 秒，模型输出 5.413 秒，可见文字 5.451 秒（38 ms 后）。不是 UI 或 SQLite 阻塞。整个 worker 进程 CPU 累计仅 1.26 秒，低于首次解码墙钟时间；足以排除这 4.23 秒全部是该进程 CPU 忙等，不能据此断言是哪一个 GPU、权重分页或系统调度事件。

本轮给已有原生 `sample` 诊断增加从进程启动采样的选项（旧选项在 8 秒后才开始，漏掉首次解码）。只采样自行启动的隔离 App 与唯一子 worker。实际原速同 WAV 的首解码为 238 ms，未重现 4.231 秒长尾；profile 数据是诊断，不用于性能改善分数。完整 Xcode/Instruments/xctrace 在此 Mac 不可用，不能称已运行 Instruments。后续最终候选使用无采样的交错原速配对。

没有重复 Metal 缓存实验，没有改变 Qwen 权重、解码、VAD、稳定前缀或 EOS。对未复现的偶发首次解码停顿不宣称根治。阶段时间线和采样原件见 `evidence/release-101/performance/`。

## 质量口径纠正

原报告中 420 段 CER 8.53% 来自 `MandarinCohort` 每 200 ms PCM 仅等待 3 ms 的加速回放。这证明产品链路质量，不证明原速。本轮给同一夹具加入显式 `realtime` 模式，按单调时钟向每块 PCM 的实际结束时间投递；记录音频帧数、投递时长、最大落后、EOS 定稿耗时及 WAV SHA。保留 accelerated 默认与历史原件，既不改参考文本/评分分母，也不把 CLI 音频节拍冒称 AppKit 可见延迟。

15 段与 38.8 秒长句继续使用实际 AppKit 文字观测。420 原始样本与 20 派生低音量/噪声样本分开计分。候选未运行的结果均为 NOT_RUN，完成后补入最终 ACCEPTANCE。
