## 已安装 533 的原生确认

533 与上表 527 的识别器、发布逻辑、模型清单及 worker 相同；两者间的产品修改是选择性窗口避让。用最终 Developer ID 二进制原速重跑五个历史问题样本。五条均在讲话中多次显示，11 块原音和五份最终文字、复制结果均与 527 一致。这个困难子集含 204 个参考字，32 个错误（15.69%）；不能与全量 CER 混算。首个正确双字 P50/P95 为 0.689/1.080 秒，有效更新间隔为 0.401/1.078 秒，停讲到定稿为 0.028/0.097 秒。某条录音在 4.142、4.179、4.694 秒顺次显示「通」「通过」「通过红外」，EOS 在 15.502 秒。五例另有 2.406 和 3.700 秒的末尾静默或稀疏语音区间。此处五例与高负载长句的中段停显是两项不同观测。[终包原生收据](../../../evidence/internal-0.20-533/recognition/RESULT.json) · [当时的窗口](../../../evidence/internal-0.20-533/recognition/partial-native533.png)

对照的 38.8 秒长句在两次无竞争轮的宿主与 worker 合计分别用了 12.44 / 25.81 CPU 秒（497）和 13.24 / 22.10 CPU 秒（修复后）。两个竞争轮为 21.45 / 19.11 和 18.29 / 19.28 CPU 秒。两版实测同时峰值物理占用分别为 1,692–1,804 与 1,689–1,823 MiB。未观察到一致的总 CPU 或内存改善。高负载中段停显、8 GB Mac 及长期电池影响仍需分别验收。


38.8 秒的同一轮竞争测试有两处不同原因的停顿。在第一次切段时，worker 用 2.528 秒精确解码 30.08 秒完整录音，之前的临时结果只覆盖 29.40 秒。多出来的 0.68 秒带来了句尾的「声光」，解码完成后 19.9 毫秒即在窗口可见。另一处 3.429 秒内窗口曾改字，但参考文本中的新双字没有继续出现。期间模型两次改写前词，最终候选在 27.5 毫秒内到达窗口。进程采样无法再分开解码内部的 CPU 执行、线程调度与 GPU 等待。[逐次解码、时间轴和窗口原始记录的复算](../../../evidence/next-release-recognition/loaded-gap/README.md)
