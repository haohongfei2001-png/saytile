# Saytile — 中断前两项关键接口修订（恢复约束，不是假称已获取原版）

来源：用户提供的 Pro 会话截图（2026-11-06 01:48 左右）。

## R1. “只删除原音”必须保留文字

- 删除动作需有独立明确语义：`delete_audio_keep_transcript` 与 `delete_record` 严格区分。
- 只删原音时，保留 `utterances` 和 `transcript_revisions`、用户编辑版本、文字搜索和历史引用；原音相关索引应更新为已删除/不可回放，不再指向不存在的文件。
- 将物理删除与数据库状态更新分开：先提交独立的持久化删除意图，再执行安全清理，崩溃恢复可继续完成。
- 共享 PCM 文件包含其他仍被引用的范围时，必须安全重组或延迟回收；不能删除仍被其他记录依赖的声音。
- 清理原音不应复用原 schema 中含记录删除语义的 `utterance`/`generation` tombstone；恢复扫描不得将已删除原音自动“复活”。
- 验收包括：仅删原音后全文、修改稿、搜索与复制仍可用；重启恢复后不能重新导入被删原音；共享块范围不误删。

## R2. 连续直接输入应有稳定前缀派发边界

- ASR 的临时/最终文本可以不断改写；“出现新 revision”不能视为“整段文字应该重新插入”。
- 每个真实绑定的编辑目标 / 输入会话必须保存已经派发的**稳定**文本范围及其文本快照；采用 UTF-16 安全偏移，并保证每个范围至多尝试派发一次。
- 只有稳定前缀与已派发快照一致时，才增量插入尚未派发的后缀；否则暂停该目标的自动追加并提示检查，不能把修订后的整句重复追加。
- `dispatching` 后崩溃的结果为未确认，不自动重发；不应因此全局阻止新的独立段落。
- 绑定目标失效、用户切换聊天、改选区、程序重启，应废弃旧绑定而不是继续向未知目标插入。
- 逐个区分“已复制”“已投递/未确认”“已插入确认”，不修改已有正文，也不自动发送。
- 验收包括：增量文本 `你好` → `你好，世界` 只插入后缀；同一前缀的新 revision 不重复；前缀回写变更不盲目追加；重启后不自动重放未确认提交。
