# Qwen PCM packet boundary review

The current Chinese official [Message Python SDK documentation](https://help.aliyun.com/zh/model-studio/qwen-asr-message-python-sdk) expressly describes approximately 100 ms / 1–16 KB packets as a recommendation, both in the streaming instructions and the `send_audio_frame` table. The English translation uses more imperative wording. The [Message client-event contract](https://help.aliyun.com/en/model-studio/qwen-asr-message-client-events) and [WebSocket interaction contract](https://help.aliyun.com/en/model-studio/qwen-asr-message-websocket-api) establish task readiness, mono audio, sample format and EOS; they do not specify rejection of sub-1 KB PCM frames.

The SDK's own local-file example sends `min(chunk_size, remaining_bytes)` and then EOS, without padding the final short frame. Therefore these documents do not establish a hard 1 KB minimum for every frame. No provider protocol or production PCM path was changed based on an unproven hard constraint. Actual cloud acceptance and the relative latency/efficiency of 20 ms versus 100 ms remain unverified.

The production VAD path admits 20 ms / 640-byte PCM frames. The new `productionTwentyMillisecondFramesAndShortTailKeepExactPCM` loopback test feeds both production ASR clients 50 paced 640-byte frames plus a final 198-byte tail. It asserts exact 32,198-byte SHA-256 identity and EOS at both peers, Qwen's unchanged 640-byte frames/198-byte tail, and Assembly's documented frame-duration bounds after its existing no-padding packetization. This adds production-sized transport coverage; the simulator cannot prove how the real Qwen service treats those packets.

At this report's creation the new test is ready for the owner's scheduled final full-native run with the server enabled; the earlier protocol receipt covers 100 ms input blocks. Do not count this additional scenario as passed until that run records it. No source provider change, real API request, microphone or personal recording was used for this review.
